## 1. 개요

### 1.1 배경 및 문제 정의

이 프로젝트는 꽃다발 주문 도메인에서 **재고 동시성 제어, 캐싱 전략, 인증 구조 설계, 배포 자동화**를 구현해 실무형 백엔드 역량을 증명하는 포트폴리오 프로젝트다. 꽃말·상황별 태그를 데이터 모델에 반영하고, 꽃다발·화환·꽃바구니·화분 등 식물 전반을 다루는 커머스 경험을 지향한다.

### 1.2 목표

- JPA 연관관계 설계 및 N+1 문제 해결 경험 확보
- Redis를 캐싱·동시성 제어(재고)·중복 주문 방지·랭킹에 적용
- JWT 기반 인증 구조 직접 설계 및 구현
- Docker 기반 환경 일관성 확보 및 실배포 완주
- 캐싱과 동시성 처리의 개선 효과를 수치로 증명

### 1.3 성공 지표 (KPI)

| 지표             | 목표                                                     |
| ---------------- | -------------------------------------------------------- |
| 재고 동시성 제어 | 동일 상품 동시 주문에서 오버셀(재고 음수) 0건            |
| 캐싱 성능 개선   | 상품 상세 조회 API 응답 시간 50% 이상 단축               |
| 중복 주문 방지   | 동일 멱등키 재시도에서 신규 주문 생성 0건                |
| N+1 해결         | 주문 목록 조회 쿼리를 페이지당 상수(1~2개) 수준으로 유지 |
| 배포 완주        | Docker Compose 기반 실서버 배포 및 외부 접속             |

### 1.4 범위

**In-scope (MVP)**: 회원가입/로그인, 상품 목록·상세·필터링, 장바구니, 주문 생성·목록·상세 조회, 재고 동시성 제어, 중복 주문 방지

**Should-have**: 인기 꽃다발 랭킹

**Out-of-scope**: 실제 PG 결제 연동, 리뷰/평점, 관리자 페이지, MSA 전환, Kubernetes 배포, 알림

## 3. 기능 요구사항

### FR-1. 회원가입 / 로그인 — Must

- 이메일/비밀번호 기반 회원가입, BCrypt 해싱 저장
- 로그인 성공 시 Access Token(JWT)과 Refresh Token 발급
- 중복 이메일은 409, 8자 미만 비밀번호는 400, 로그인 응답에는 Access Token과 만료 시간 포함

### FR-2. 상품 목록 / 상세 조회 — Must

- 카테고리별 페이징 목록과 상품 상세를 제공한다.
- 상세에는 색상, 꽃말, 가격, **Redis에서 읽은 최신 재고**를 표시한다.
- 상품 기본 정보는 Redis에 5~10분 캐싱한다. 가격·상품 정보 변경 또는 주문 성공 후 상세 캐시를 무효화한다.
- 캐시 히트 시 상품 기본 정보 DB 쿼리가 발생하지 않아야 한다.

### FR-3. 상품 필터링 — Must

- `occasionTag`, 다중 조건 조합과 페이징을 지원한다.
- 인덱스를 적용해 10만 건 이상에서도 로컬 기준 300ms 이내 조회를 목표로 한다.

### FR-4. 장바구니 — Must

- Redis Hash `cart:{userId}`로 장바구니를 저장한다. 필드는 `productId`, 값은 수량이다.
- 추가, 수량 변경, 삭제, 조회를 제공한다.
- TTL은 설정하지 않으며 로그아웃 후에도 유지한다.
- 수량은 1 이상이어야 하며, 수량 변경은 지정 수량으로 교체한다.

### FR-5. 주문 생성 — Must

- 배송 희망일자·시간대와 메시지카드 문구를 포함해 주문을 생성한다.
- 주문의 상품 가격과 이름은 주문 상품에 스냅샷으로 저장한다.
- Redis Lua 스크립트로 모든 주문 상품의 재고를 확인하고 차감한다. 하나라도 부족하면 어느 상품도 차감하지 않는다.
- Redis 차감 뒤 DB 주문 저장 트랜잭션이 실패하면, 이미 차감한 수량을 Redis Lua 스크립트로 보상 증가한다.
- DB 트랜잭션 커밋 후 상품 상세 캐시를 무효화한다. 상품 상세 응답의 재고는 캐시 본문이 아니라 Redis 재고 키에서 별도 조회한다.
- 재고 부족 시 `409 INSUFFICIENT_STOCK`을 반환한다.
- 재고 100개에 동시 주문 200건이면 정확히 100건만 성공해야 한다.

### FR-6. 중복 주문 생성 방지 — Must

- `POST /api/orders`는 `Idempotency-Key` 헤더를 필수로 받는다. 키는 사용자별 네임스페이스로 분리한다.
- 최초 요청은 처리 중 상태를 원자적으로 선점한다.
- **완료된 동일 키 요청은 저장된 첫 성공 응답을 그대로 재반환하며 새 주문을 만들지 않는다.**
- 동일 키 요청이 아직 처리 중이면 `409 REQUEST_IN_PROGRESS`를 반환한다.
- 완료 응답은 Redis에 5초간 보관한다. 처리 중 잠금은 주문 처리 중 만료되지 않도록 별도 TTL을 둔다.

### FR-7. 주문 내역 조회 — Must

- 내 주문 목록 및 주문 상세를 제공하고, 주문·주문상품·상품 스냅샷을 함께 조회한다.
- 목록과 상세는 본인 주문만 조회할 수 있어야 한다.
- 목록 조회에서 Fetch Join, `@EntityGraph`, `@BatchSize` 등을 사용해 N+1을 방지한다.

### FR-8. 인기 꽃다발 랭킹 — Could

- 조회수/판매량 기반 실시간 랭킹을 Redis Sorted Set으로 관리한다.
- 랭킹 갱신은 상품 조회 API의 응답 지연에 영향을 주지 않도록 비동기 처리를 고려한다.

## 4. 비기능 요구사항

| 구분   | 요구사항                                                                                                 |
| ------ | -------------------------------------------------------------------------------------------------------- |
| 성능   | 상품 상세 캐시 히트 P95 100ms 이내, 캐시 미스 P95 300ms 이내(로컬 기준)                                  |
| 동시성 | 재고 차감의 원자성을 보장하고 오버셀 0건                                                                 |
| 확장성 | 상태를 WAS에 두지 않는 Stateless 구조                                                                    |
| 가용성 | Redis 캐시 장애는 DB 직접 조회로 처리한다. 단 재고·멱등성 Redis 의존 기능은 503 처리한다.                |
| 정합성 | 주문 저장 실패 시 Redis 재고 보상 증가를 수행하고, 보상 실패는 오류 로그·알림 및 재조정 대상으로 남긴다. |
| 보안   | JWT 서명 키 환경변수 분리, HTTPS 적용, 로그인 Rate Limiting 고려                                         |
| 테스트 | Testcontainers(PostgreSQL) 통합 테스트와 멀티스레드 동시성 테스트                                        |
| 관측성 | 캐시 히트/미스, 재고 차감·보상 실패, 멱등키 상태를 로깅                                                  |

## 5. API 명세

| 구분     | Method | Endpoint                | 설명                                   | 인증 필요     |
|----------|--------|-------------------------|----------------------------------------|---------------|
| 인증     | POST   | `/api/auth/signup`      | 회원가입                               | X             |
| 인증     | POST   | `/api/auth/login`       | 로그인, 토큰 발급                      | X             |
| 인증     | POST   | `/api/auth/reissue`     | Access Token 재발급                    | Refresh Token |
| 상품     | GET    | `/api/items`            | 목록 조회(필터, 페이징)                | X             |
| 상품     | GET    | `/api/items/{id}`       | 상세 조회                              | X             |
| 장바구니 | GET    | `/api/cart`             | 장바구니 조회                          | O             |
| 장바구니 | POST   | `/api/cart`             | 장바구니 상품 추가                     | O             |
| 장바구니 | PATCH  | `/api/cart/{productId}` | 해당 상품의 수량을 지정 수량으로 변경  | O             |
| 장바구니 | DELETE | `/api/cart/{productId}` | 장바구니 항목 삭제                     | O             |
| 주문     | POST   | `/api/orders`           | 주문 생성. `Idempotency-Key` 헤더 필수 | O             |
| 주문     | GET    | `/api/orders`           | 내 주문 목록 조회(페이징)              | O             |
| 주문     | GET    | `/api/orders/{id}`      | 내 주문 상세 조회                      | O             |

### 5.1 응답 포맷

```json
{
  "success": true,
  "data": { "id": 1, "name": "핑크 로즈 부케" },
  "error": null
}
```

```json
{
  "success": false,
  "data": null,
  "error": { "code": "INSUFFICIENT_STOCK", "message": "재고가 부족합니다." }
}
```

### 5.2 주요 에러 코드

| 코드                  | HTTP Status | 상황                            |
| --------------------- | ----------- | ------------------------------- |
| `DUPLICATE_EMAIL`     | 409         | 이미 가입된 이메일              |
| `INVALID_CREDENTIALS` | 401         | 로그인 정보 불일치              |
| `INSUFFICIENT_STOCK`  | 409         | 재고 부족                       |
| `REQUEST_IN_PROGRESS` | 409         | 같은 멱등키 요청이 아직 처리 중 |
| `TOKEN_EXPIRED`       | 401         | Access Token 만료               |

완료된 멱등 요청은 에러가 아니라 최초 성공 응답을 동일하게 반환한다. 세부 API 스펙은 Swagger(springdoc-openapi)로 자동 문서화한다.
